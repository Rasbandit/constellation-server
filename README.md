# constellation-server

Rust server for Constellation, compatible with Archipelago clients through a single compat crate (`edge-compat`).
Design lives in the sibling `constellation` repo, `docs/design/05-rust-architecture.md` (workspace, section 6) and `DECISIONS.md` (D-78: all Rust).

Status: first milestone (D-100). One process hosts one room from a seed bundle, or one room per bundle in a folder, and serves clients compatible with Archipelago; the log is in Postgres when a database URL is set (the room survives a restart or a crash, D-98), otherwise in memory. A proof of concept, not for production use; the plan is [`docs/ROADMAP.md`](docs/ROADMAP.md) and how to help is [`CONTRIBUTING.md`](CONTRIBUTING.md). Text mentioning Archipelago needs the review in the design repo's `CLAUDE.md`. What the compatible edge supports, with the test that proves each part: [`docs/compat-status.md`](docs/compat-status.md).

Container image, compose file and how clients reach a room: [`docs/container.md`](docs/container.md).

## Layout
- `crates/proto`: wire ids and the error registry (doc 01 D1.7). Leaf crate, no IO. Also `Command`, `Event` and the id newtypes (`Cid`, `RoomId`, `Epoch`, `Timestamp`). `proto::cwp` holds the CWP v1 wire types (design doc 01 D1.10, proposal D-123): the frames, validated names, the integer range, the type and path registries, typed decode and encode, and a message codec that still answers a frame it cannot decode. The generated schema is committed at `crates/proto/schema/cwp-v1.json` (validate against `#/$defs/ClientFrame` and `#/$defs/ServerFrame`; the file's root also carries the registry, paths and error table under keys that are not JSON Schema keywords); a snapshot test compares it as JSON and, on a change, writes the new one to the system temp directory for review. Golden transcripts in `crates/proto/golden/` are replayed by a checker that enforces the D1.10 rules (ordering, dedupe, audience, replay, results), and a set of wrong transcripts proves each rule is enforced.
- `crates/spec-rng`: the pinned random stream and sampling rules (doc 01 D3.2), with golden vectors from an independent Python reference.
- `crates/config`: the only home of limits and the only crate that reads environment variables (doc 05 6.2 rule 5). `no_std` without the default `std` feature (only `load` needs std).
- `crates/room-core`: the pure room state machine (`RoomState`, `apply`, `fold`), `no_std` + alloc. No clock, no rng, no IO.
- `crates/log`: the `LogStore` seam with epoch-fenced append (doc 05 7.2), `MemLogStore` for tests and the simulator, and `PgLogStore` (feature `postgres`, sqlx, D-98). One contract suite (`src/contract.rs`) runs against both stores. Migrations are plain SQL in `migrations/`, applied by the server at start.
- `crates/sim`: the deterministic simulator. `cargo test -p sim` runs `SIM_SEEDS` seeds (default 64); `SIM_SEED=<n> cargo test -p sim` replays one.
- `crates/seed-bundle`: the JSON seed bundle schema (one room's slots, placements, data packages, `slot_data`, options) and its validation on load.
- `crates/runtime`: the room actor on tokio (D-99: an in-process seam). Applies command batches, appends them in one fenced write, publishes, then replies (the hold rule).
- `crates/edge-compat`: the Archipelago wire protocol as serde types and the per-connection session; the only crate that knows that protocol (doc 05 6.2 rule 2).
- `crates/server`: the `constellation-server` binary (axum for HTTP, yawc for the WebSocket, D-97).
- `crates/e2e`: end-to-end helpers (start the real binary, a yawc client, the fixture) and the fixture itself. The scenarios are integration tests of `server` (`crates/server/tests/compat.rs`), so cargo builds the binary and hands its path over (`CARGO_BIN_EXE_constellation-server`).
- `crates/e2e-ap`: the interop test with `archipelago_rs` (MIT), used as a path dependency from the sibling `Archipela-Go` checkout; no source of it is in this repo. Its own workspace, excluded from the main one, because cargo resolves every path dependency (even an optional one); CI does not have that checkout, so CI does not run it (run `just e2e-ap` locally before merging edge changes). Its lint table is a copy of the workspace's, kept equal by a test in `crates/e2e`.
- `tools/ap-import`: Python importer from a seed made by Archipelago's generator to our bundle.
- `tools/ap-gen`: the generation sidecar the server runs in its sandbox: inspects uploaded `.apworld` and player `.yaml` files, and generates a seed with an Archipelago checkout, converted by `tools/ap-import` (see "Uploads and seed generation").
- `tools/ap-client-check`: drives the real server with Archipelago's own `CommonClient` from the sibling checkout (connect, `SetNotify`, `Set`, `Get`, start items, client status, `!hint`, the hints key and `UpdateHint`). Local only: `just ap-client-check`.

Next crates, in doc 05 section 20 order: `edge-native`.

## Run the server
```sh
cargo run -p server --bin constellation-server -- --bundle crates/e2e/fixtures/two-slot.json --port 38281
```
Then point a client compatible with Archipelago at `ws://localhost:38281` with slot `Alice` or `Bob` and game `Archipela-Go 2: Electric Boogaloo`. Flags: `--host <ip>` (default 127.0.0.1).

### Several rooms
`--rooms <folder>` in place of `--bundle` lists one room per `*.json` seed bundle in the folder (at most `max_rooms`, 1 000, in `crates/config`). Each room gets a random room key (D-12: 10 characters, `a` to `z` and `2` to `7`) and logs it: `room ready key=<key> seed=<seed name>`. `CONSTELLATION_ROOM_PASSWORD` applies to every room.

Rooms come from the directory, not the folder (doc 02 section 4.3). With Postgres the directory is the `rooms` table (`migrations/0002_room_directory.sql`): the key and the bundle file are stored with the room, and a restart lists every stored room that has not finished, under the same key, even if its file has left the folder. In memory the server keeps the directory itself, and a restart loses it. The folder is a way to add rooms: every `CONSTELLATION_ROOMS_SCAN_MS` (2 000) the server lists each new bundle, so adding a room is copying a file in. Write it under another name and rename it to `*.json`, so a scan never reads half a file. The folder may start empty. A bundle that does not make a room (invalid, a stored room made from another bundle or finished, past `max_rooms`) is skipped with a warning and tried again when the file changes; a running room's file is not reread.

A listed room is loaded into memory on its first connect, and leaves memory after `CONSTELLATION_ROOM_IDLE_SECS` (900, 15 minutes, a design value) with no connection; its next connect loads it again from its log. At most `CONSTELLATION_MAX_RESIDENT_ROOMS` (250) rooms are in memory at once: a room that must load past that puts the room unused for the longest to sleep first, and a room with a connection open is never put to sleep, so when every one has one the new room is refused until one frees. A room with no connection for `CONSTELLATION_ROOM_ABANDON_SECS` (2 592 000, 30 days, D-30) ends as abandoned: it is no longer served, Postgres marks it finished so a restart does not bring it back, and its data is kept. The database decides: the server records when each room was last used (at once when a room leaves memory or the server stops cleanly, otherwise at most every `CONSTELLATION_ROOM_TOUCH_SECS`, 60, so a crash loses at most that much), and a room the database saw used since is not ended. What happens to a finished room's data afterwards, and the other ways a room ends (every goal reached, the host closes it), are #56. One room's trouble does not stop the others: a room whose task fails is loaded again from its log on its next connect, under the same key. A room that fails to load, or stops within `CONSTELLATION_ROOM_HEALTHY_SECS` (30) of loading, is not loaded again until a wait has passed: `CONSTELLATION_ROOM_RETRY_FIRST_MS` (1 000), doubled for each such failure in a row, at most `CONSTELLATION_ROOM_RETRY_MAX_MS` (60 000); connects meanwhile get the 503 below. A fenced room still ends the process. With `--bundle` the room is loaded at startup, never leaves memory and is never abandoned, and its end is the process's end.

A client reaches a room through its key in the path: `ws://<host>:<port>/<key>`. The server reads the path of the WebSocket request; case does not matter. With `--bundle`, every path reaches the one room (so `ws://localhost:38281` keeps working). With `--rooms`, a path that names no room, or an unknown key, gets HTTP 404, even when only one room is listed: the list changes while the server runs, so an old link must never land in another room. A listed room that fails to load gets HTTP 503 with a generic message; the reason is in the server log. One host name and one ordinary TLS certificate serve every room, so no wildcard DNS or wildcard certificate is needed; a proxy in front must pass the path through unchanged.

`--port 0` picks a free port; the bound address is logged. `GET /healthz` answers `ok`. `GET /version` answers the build version.

`--web-dir <folder>` serves the built web UI (`web/`, `bun run build` then `bun scripts/precompress.mjs`) on the same port: `/` and every other plain GET is the UI (a file from the folder, else `index.html` for a page load; a missing file or `/assets/*` path is a 404), while a WebSocket upgrade on `/<key>` still joins the room, and with `--bundle` an upgrade on any path does. The container image sets it. The admin API is on this same port under `/api` (token-gated, below); see `docs/container.md` for a reverse proxy. SIGTERM or Ctrl-C stops it.
The room password is never a flag (it would show in `ps`): set `CONSTELLATION_ROOM_PASSWORD`, or `CONSTELLATION_ROOM_PASSWORD_FILE` to a file whose first line is the password; it overrides the seed's. Limits come from `crates/config` (design values), some overridable by environment: `CONSTELLATION_MAX_CONNECTIONS` (10 000; over it, HTTP 503), `CONSTELLATION_CONNECT_TIMEOUT_MS` (30 000: a socket with no slot connected by then is closed), `CONSTELLATION_IDLE_TIMEOUT_MS` (60 000) and `CONSTELLATION_PING_INTERVAL_MS` (20 000).

### With Postgres (the room survives restarts)
Set `CONSTELLATION_DATABASE_URL` (or `CONSTELLATION_DATABASE_URL_FILE`, a file whose first line is the URL; never a flag, since the URL can hold a password) to a database the server may create tables in, for example `postgres://constellation@localhost/constellation`. At Stage 0 and 1 Postgres runs on the same box (doc 12), no pooler in between. On start the server applies the migrations, claims the room (bumping its owner epoch, so an older process still running can no longer write), and rebuilds it from the log before it listens; the log line `room loaded ... events=<n>` says how much it read. The room id comes from the seed name; a restart with a different bundle under the same seed name is refused. Without a URL the server logs `log store: IN MEMORY` as a warning and a restart loses the room. Pool size and session timeouts come from `crates/config` (design values): `db_pool_connections` 8, `statement_timeout` 10 s, `lock_timeout` 5 s, `idle_in_transaction_session_timeout` 10 s. A URL parameter sqlx does not recognise is refused at start (sqlx would log it with its value). If the room stops (its log refused or failed a write) the process exits non-zero so a supervisor restarts it and the room reloads; `GET /healthz` answers 503 `room stopped` meanwhile.

Exit status: 0 after SIGTERM or Ctrl-C, also during startup (it abandons startup); 3 when a newer owner took the room (the log line says `fenced by a newer owner current=<epoch>`): do not restart it, or two instances on one database fence each other in a loop; 1 for every other failure, including a room whose log write failed: restart it, it reloads from the log. A systemd unit (example, not shipped yet):
```ini
[Service]
ExecStart=/usr/local/bin/constellation-server --bundle /srv/constellation/seed.json --port 38281
EnvironmentFile=/etc/constellation/env
Restart=on-failure
RestartPreventExitStatus=3
```

### Uploads and seed generation (admin API)
With `--data-dir <path>` the server also serves an admin API that stores uploaded worlds and player files and generates a seed bundle from a chosen set of them. A finished world's seed (v2, `docs/seed-bundle-v2.md`) and its game packages go into the server's store (Postgres with `CONSTELLATION_DATABASE_URL`, else memory), never into files; with `--rooms` as well, it is listed as a room at once. A world whose seed name the server already hosts fails instead of sharing that room. The rooms folder is only an import path for v1 bundle files (`*.json`): a listed room loads from the store. The server refuses to start with `--data-dir` unless all of these are set: `CONSTELLATION_AP_DIR` (an Archipelago checkout), `CONSTELLATION_AP_PYTHON` (a Python with its dependencies) and `CONSTELLATION_AP_GEN_SCRIPT` (`tools/ap-gen/ap_gen.py`, absolute path). The API is served on the room's own port under `/api` (checked before a room key and the web UI, so nothing can shadow it): it runs uploaded code, so put a TLS reverse proxy in front and never expose plain HTTP over a network. Wrong tokens are counted per client address and get 429 past a burst; `--trusted-proxy-header <name>` takes the address from a proxy's header instead of the peer (off by default; `docs/container.md`). **Open mode is the current default:** with no `CONSTELLATION_ADMIN_TOKEN` (or `CONSTELLATION_ADMIN_TOKEN_FILE`) every route is open and the server logs a warning at start, so anyone who can reach the port can upload and run world code inside the sandbox (restrict the port, or set a token). With a token, every route needs `Authorization: Bearer <token>`; the token must be at least 32 bytes (`openssl rand -hex 16`); `GET /api/auth` stays open and says only whether a token is required. Uploads are raw request bodies, not multipart:
- `PUT /api/apworlds?name=<file>` and `PUT /api/yamls?name=<file>` (percent-encode the name): the body is checked by the sandboxed sidecar, then stored in the server's store (Postgres with `CONSTELLATION_DATABASE_URL`, the `world_uploads` table; else in memory), once per kind and sha256, with its record beside it, so every server instance sees it. Its game is the inspected game name reduced to `a-z`, `0-9`, `_` and `-` (at most 64 characters; `unknown` when there is none); a yaml that names several games is `mixed`. Files an earlier version kept under `<data-dir>/apworlds/` and `<data-dir>/yamls/` (by game or flat) are moved into the store at startup, each checked against its sha256, and on Postgres removed once stored; one that does not match stays, with a warning. The kinds, their folders and extensions are one table in `crates/server/src/worlds.rs`. Replies `201` with `{id, name, bytes, ...}` (for an apworld its `module`, `game`, `world_version` and other manifest fields; for a yaml its `players`). The same content again replies `200` with the stored record. Caps: 64 MiB per apworld, 1 MiB per yaml.
- `PUT /api/manifests?name=<file>`: a data-only world manifest (JSON with a `game` and a `version`). It is checked by the engine in a capped child process (nothing in it runs as code; the full schema validator is #27), then stored in the database (`world_manifests`, migration 0004; in memory without `CONSTELLATION_DATABASE_URL`), once per content hash, never as a file. The body is cut off at 8 MiB while it is read. Replies `{id, name, bytes, game, version, items, locations}`; the same content again replies `200` with the stored record and no check.
- `GET /api/apworlds`, `GET /api/yamls`: the stored records. `GET /api/manifests?limit=&after=&game=`: a page of manifest records ascending by id, `{items, next}` (`next` is the `after` of the following page, null on the last; a page holds at most `list_page_max` records), read from columns, never by parsing a manifest.
- `POST /api/worlds` with `{"apworlds": [ids], "yamls": [ids]}`: replies `202` with `{id, status: "queued"}`. Generations run one at a time.
- `POST /api/worlds` with `{"manifest": id, "yamls": [ids]}`: the same job, status, queue and hosting, but the data-fill engine fills the world in a child process (`engine: "data-only"` in the status; no sidecar, no world code) under address-space, CPU, open-file and process caps, a wall-clock kill and an empty environment (`fill_*` limits; no sandbox, since it reads data, never code; the process cap counts every task of the server's user, so it is a brake, and 0 turns it off). Player files are JSON documents with a `name`, a `game` (the manifest's; the API refuses another with 400) and the engine's instance (options, locations, pool, item classes, start items), uploaded through `PUT /api/yamls`. YAML player files for manifest worlds are #114.
- Capacity: at most `gen_concurrency` generations run at once and `gen_queue_max` are queued or running; a request past that, or a manifest check past `manifest_check_concurrency`, gets `503` with `Retry-After`. Each client address may upload or request a generation `admin_write_burst` times in a burst, then `admin_write_refill_milli_per_sec` per second (`429` with `Retry-After` past it). The limits are in `crates/config`; the queue and the rate table are per server process, not shared between instances (see the issue on a shared job queue).
- `GET /api/worlds/<id>`: `{status: queued|running|done|failed, ...}`, with `error` on failure, and `seed_name`, `slots` and `bundle_hash` (of the sidecar's v1 bundle, which the server converts to v2 and stores) once done. The job's copies of its inputs are removed when it ends; only `status.json` stays in `<data-dir>/worlds/<id>/`.
- `GET /api/worlds/<id>/bundle`: a finished world's seed, decoded from the store back to the v1 bundle JSON (for reading and debugging). The status is kept on disk, so a restarted server still reports it. A job that was queued or running when the server stopped is marked failed. With `--rooms`, also `room_key` and `address` (`{public host}:{port}/{room_key}`, the host from `--public-host`, default `localhost`) once the room is listed.
- `GET /api/worlds/<id>/room` (with `--rooms`): the running room, read-only: `seed`, `room_key`, `address`, `options` (`password` as a flag only, `hint_cost`, `release_mode`, `collect_mode`) and per slot `name`, `game`, `connected` and `clients` (live sessions), `checked` of `locations`, `items_received` (from checks) and `goal`. A cold room is loaded to answer. `404` when the world has no room here, `503` when the room cannot answer now.
- `GET /api/worlds/<id>/room/events`: the room's events as server-sent events: `item`, `checked` and `goal` (durable; the SSE id is the room `seq`, so a reconnect resumes with `Last-Event-ID`), and `join`, `leave` and `chat`. A resume past the room's head (it restarted from an empty log) or more than `view_history_events` (400) back starts with `{"kind": "reset"}` and the newest 400 events; a new stream gets the newest 400 without a reset. At most `view_streams` (64) streams are open at once (`503` past that); an open stream keeps the room in memory.

Generation follows Archipelago's own flow (`Generate.py` rolls the player settings from the yamls, `Main.py` writes the multidata; `WebHostLib/generate.py` does the same for the web host) with spoilers off. Patch files are still written, because Archipelago's `--skip_output` also skips the multidata, but we ignore them. Limits come from `crates/config`: `CONSTELLATION_GEN_TIMEOUT_MS` (15 minutes, then the job is killed) and `CONSTELLATION_GEN_MEMORY_BYTES` (4 GiB address space). Inside the sandbox the checkout's `worlds/` shows only its top-level files and `generic`, so the core worlds are not loaded (faster, and less code runs).

**Security model.** An `.apworld` is Python code, and generating runs it, so anyone who can upload and generate can run code on this machine. That is why the API is meant to be admin-only (a token of at least 32 bytes on every route, once set; see open mode above) and every sidecar call (inspect and generate) runs in bubblewrap (`crates/server/src/sandbox.rs`; needs `bwrap` 0.8 or newer and `prlimit`). Inside the sandbox: no network, no environment from the server (not even bwrap's own process, which stays visible there), no further user namespaces, no capabilities. The whole tree is read-only (`/`, `/dev`, `/usr`, the Python install, the checkout, the two sidecar folders under `tools/`); the only writable places are tmpfs mounts capped at 256 MiB each (`/tmp` and the generator's scratch output). No host folder is writable: the bundle comes back on stdout (capped at 65 MiB), the server writes it into the job folder and checks it with `load_bundle`. It sees only the job's chosen apworlds (mounted as the checkout's `custom_worlds/`) and yamls. Startup refuses a configured path whose mount would show the root, the home folder, the data folder or a secret file (`CONSTELLATION_*_FILE`), and a Python link in a broad folder (like `~/.local/bin`) is recreated as a link instead of mounting the folder. The process runs under `prlimit` (4 GiB address space, 64 processes and threads, 256 MiB per file, 256 open files), a wall-clock limit (killed and reaped on expiry), and dies with the server. Its stderr is read as it comes and only the last 16 KiB are kept. Inspect reads the zip and yaml as data and never imports world code. It refuses absolute paths, `..`, symlinks, more than 20 000 entries and more than 256 MiB unpacked. Yamls are read with `yaml.safe_load_all`. Each job also runs in its own cgroup (`systemd-run --user --scope`, 4 GiB `MemoryMax`, no swap, 80 tasks), which counts what the address space cap misses (tmpfs, memfd and shared memory pages, all processes together), so an out-of-memory kill lands on the job, not the server; open files are capped at 256. The server refuses to start with `--data-dir` when `systemd-run --user` cannot make such a scope. Known gaps: There is no seccomp filter (bubblewrap takes a compiled BPF program; not worth a libseccomp dependency for this POC). CPU is bounded only by the time limit. The sandbox runs as the server's user, so a kernel escape from it would reach the data folder.

Real end to end with your own files (they are never committed): `just ap-gen-check [<apworld>] [<yaml>]` (defaults: `~/Downloads/mm_2ship.apworld` and `~/Downloads/Majoras Mask.yaml`). It needs `../Archipela-Go/.ap` and its `apworld/.venv`, and prints the seed, slots, locations and timing.

## Regenerate the fixture
The fixture is a two-slot seed of the owner's game (player options in `crates/e2e/fixtures/players/`), made with Archipelago's own generator and the Archipela-Go apworld, then converted by `tools/ap-import`. The raw `.archipelago` file is not committed.
```sh
ROOT=$PWD; AG=$(realpath ../Archipela-Go); PY=$AG/apworld/.venv/bin/python; OUT=$(mktemp -d)
cd $AG/.ap
PYTHONPATH=. $PY -c 'import runpy,sys,ModuleUpdate; ModuleUpdate.update_ran=True; sys.argv=sys.argv[1:]; runpy.run_path(sys.argv[0], run_name="__main__")' \
  Generate.py --player_files_path $ROOT/crates/e2e/fixtures/players --outputpath $OUT --seed 7
PYTHONPATH=. $PY $ROOT/tools/ap-import/ap_import.py $OUT/AP_*.zip $ROOT/crates/e2e/fixtures/two-slot.json
cd $ROOT
```
Generator seed 7 reproduces the committed fixture exactly (checked 2026-11-17; Bob has a starting inventory). Importer tests: `python -m unittest discover -s tools/ap-import` (no Archipelago needed). `seed-bundle` has a test that loads the fixture, so a schema drift fails there.

## Known deviations from doc 05 7.1 and 7.2
- `Item` events carry `from` (the checking slot) and no `item_uid`, and events have no ULID id (`seq` is the id). Location and item ids are `i64`, and a location id is only unique within its slot's world, so the placement table is keyed by (slot, location).
- `Command::Goal` and `EventKind::Goal` record a slot's goal (D-100 needs it); not in the doc 05 sketch.
- `fold(snapshot, limits, tail)` takes the limits and returns `Result`; `Ctx::limits` is a borrow.
- `Applied` has one `reply` plus `depends_on` (the hold rule: do not release a reply until that `seq` is durable), and no `effects`.
- `LogStore` has `read_cursors` and no outbox rows yet. `Cid` and `RoomId` are integers.
- The Postgres schema (`migrations/0001_log.sql`) is doc 02 section 5.5 cut down: no foreign keys, unencrypted event bodies, the latest snapshot only, cursors in `slot_cursors`. `seq`, `item_seq` and epochs above `i64::MAX` are refused by `PgLogStore` (Postgres has no unsigned 64-bit type).

## Rules (doc 05 6.2)
1. L0/L1 crates never depend on tokio, sqlx, axum, a clock or an OS RNG.
2. `unsafe` is forbidden workspace-wide; exceptions go in `docs/unsafe-register.md`.
3. Only `config` reads env vars.

## Testing
Rules, layers and the end-to-end plan: [`docs/TESTING.md`](docs/TESTING.md).
- `just check`: the gate (fmt, clippy, typos, every test that needs no database including the end-to-end scenarios, docs, cargo-deny).
- `just test-pg`: adds the Postgres tests (the store contract suite on Postgres, the gate G-DB fence race and cancel tests, and the `kill -9` restart scenarios in `crates/server/tests/restart.rs`). Needs `CONSTELLATION_DATABASE_URL`; each test makes its own schema. Without the URL they fail, they never skip. The manual `nightly` workflow runs them against a Postgres 18 service container.
- `just bench-pg`: the gate G-DB throughput benchmark (the manual `nightly` workflow; not for a shared developer box).
- `just e2e`: the end-to-end scenarios alone (`cargo test -p server --test compat`).
- `just e2e-ap`: the `archipelago_rs` interop scenario; needs `../Archipela-Go`. It builds the server in the main workspace and passes its path at compile time (`CONSTELLATION_SERVER_BIN`).
- `just ap-client-check`: Archipelago's `CommonClient` against the real server; needs `../Archipela-Go` and its `apworld/.venv`. Run it before merging edge changes, like `just e2e-ap`.
- `cargo test -p server --test worlds`: the upload and generation API through the real sandbox, with a fake sidecar (`crates/server/tests/fake_ap_gen.py`); needs `bwrap` and `python3`, no Archipelago. Sidecar inspect tests: `python -m pytest tools/ap-gen/test_ap_gen.py` (needs PyYAML).
- `just ap-gen-check`: a real generation through the API (see "Uploads and seed generation").

## Dev setup
Run `just setup` once. It enables the hooks in `.githooks/`: pre-commit (fmt check), commit-msg (conventional commits, subject at most 50 chars). `just check` also needs `cargo-deny` and `typos`.
Lints: POC mode, compiler and clippy defaults plus `unsafe_code = "forbid"` (see `[workspace.lints]` in `Cargo.toml`). Warnings do not fail CI. CI runs fmt and the unit tests only.
